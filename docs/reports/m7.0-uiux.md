## 🟠 ISSUES

None of these block the manifest or the validation-batch gate — all are
engineering-judgment decisions I made as spec author to keep the plan
accurate and the generation budget sane, surfaced here for visibility
rather than silently baked in:

1. **Death-impact/death-water need no separate art (spec decision, not a
   gap).** The shipped code doesn't draw distinct death sprites — both
   reuse the base chicken art via a runtime `ctx.scale` transform (squash
   for impact, scale-to-0 for water sinking). Full replacement = apply the
   same transform to the generated `chick-idle` frame. Generating 2 extra
   "death frame" images would duplicate art that's identical to the idle
   frame under transform. Impact: zero — this matches the shipped
   technique exactly; flagging only so it's not misread as a missed
   requirement (PRD §6 lists "death-impact, death-water" as animation
   sets, and they ARE covered — just via transform-reuse, not new art).
2. **Vehicle color variants generated once, palette-swapped rather than
   regenerated 3×.** Each stage's `cars[]` array has 3 body-color variants
   of the identical silhouette. Regenerating per color would 3× the
   vehicle generation budget for zero shape difference. Spec calls for one
   canonical silhouette per {stage,kind} + a cheap post-process hue-remap
   for the other variants. Impact: reduces vehicle generation calls from a
   theoretical ~19 down to 7; no quality loss since shape is identical
   either way.
3. **Two DESIGN-vs-shipped-code drifts found (pre-existing, not
   introduced by this task).** DESIGN §6 describes a Stage-1 near-layer
   "tree silhouette clusters" and a Stage-3 near-layer "chain-link-fence"
   detail, and Stage-2 windows that "occasionally flicker" — none of these
   are actually implemented in `index.html` (only far/near hill bands,
   smokestacks, and a static non-flickering window pattern exist). Since
   M7 is an asset-swap milestone, not a new-feature pass, the manifest
   matches shipped behavior 1:1 rather than inventing new parallax
   elements. Flagging for the record in case a future milestone wants to
   close that DESIGN/code gap as an actual feature addition — out of scope
   here. Severity: Minor/cosmetic, non-blocking.
4. **`sfx-train-rush` and `sfx-eagle-grab` are net-new, not replacements.**
   Current code has no SFX during the train's `pass` state at all, and
   the eagle-grab moment currently just reuses the generic `death()` cue.
   Both are explicitly called out as additions in the SFX manifest table
   (not silently treated as if something existed to replace) — this
   matches the task's explicit ask to enumerate both as distinct SFX.
5. **Ground-tile risk is real and separately validated.** Per PLAN R13,
   diffusion models tile poorly; none of PM's originally-suggested 3
   validation-batch assets exercise tiling at all. Recommended (not
   silently added) a 4th validation asset (`tile-s1-grass`) specifically
   to surface this risk at the gate rather than first discovering it
   during the full run. See A4 in the manifest for full reasoning; this is
   framed as a confirm-or-adjust recommendation per the task's own
   instructions, not an unrequested scope change.

No PRD/DESIGN gap blocks generation from proceeding. ENV-01 (subagent HF
tool-access gap) remains OPEN and unaffected by this task — already logged.
